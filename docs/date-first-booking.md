# 日時から選ぶ予約

予約ページ `/` は、管理者が設定した1つの方式だけを表示します。管理画面の「店舗設定 → 予約画面の表示方式」で、「メニューから選ぶ」または「日時から選ぶ」を保存してください。お客様向けの切り替えボタンやURLパラメーターによる方式の変更はありません。

メニュー方式ではメニュー選択 → 日付・空き時間の選択へ進みます。日時方式では最初から日付と空き時間のカレンダーを表示し、日付 → 空き開始時刻 → メニュー・担当者 → お客様情報 → 内容確認 → 確定の順に進めます。時間を選ぶまではメニュー・連絡先フォームを表示しません。入力済みのお名前・メール・電話番号は、日時の選び直しで保持します。端末への保存は行いません。

設定変更はホームページの次回表示・再読み込みで反映します。入力中のページを途中で別方式へ切り替えません。公開ページは `/api/booking-mode` をno-storeで取得してから `MenuBooking` または `DateBooking` を描画するため、違う方式が一瞬表示されることもありません。予約・確定の処理は共通です。

## 表示と判定

- 日本時間で7日分の日付を並べ、前後への移動と日付の直接指定に対応します。受付可能な日付の範囲は既存の予約ルールを利用します。
- カレンダーの時間欄は**選択した日**だけの空き開始時刻です。7日分を一括で照会せず、日付ボタン自体は空きの有無を示しません。
- 同じ開始時刻はまとめて表示します。その時刻に施術・準備・片付けが収まる、公開中のメニューと対応可能な有効スタッフだけを案内します。メニューごとに所要時間が違っても、入らないメニューは選べません。
- `/api/date-availability?date=YYYY-MM-DD` は店舗設定からスコープを決定し、選択日の全メニュー・担当者の空きを返します。店舗IDをクライアントから受け取りません。レスポンスはメニューID・スタッフID/表示名・開始時刻のみです。
- サービス・担当者との紐付け・営業時間を各1回、確定予約・受付停止を各1回取得し、Google busyを1回更新します。メニューごと、スタッフごとの外部照会は行いません。所要時間と準備・片付けは既存の `findAvailableStarts` で判定します。前後日のバッファ、全店・担当者別受付停止も対象です。
- DB・Googleの確認に失敗した場合や、取得が1,000行に達して完全性を確認できない場合は空きを案内せずエラーにします。閉店日はGoogleの更新や予約の取得を省略します。
- 受付締切は外部照会後の時刻で再評価します。クライアントは30秒間隔・画面への復帰時に再確認し、古い日付の応答は破棄します。取得中は選択・次へ進む操作を無効にします。

## 確定と既存データ

メニュー・担当者を決めて次へ進む際、従来の `/api/availability` でも選択を再確認します。お客様情報の検証、予約確定API、Google busy確認、DBの競合防止、メール・LINE通知、変更・キャンセル用リンクは既存の仕組みをそのまま使用します。保存・通知中と完了後は空きのポーリングを停止し、確定した予約によって自分の空き枠が消えても完了画面が戻らない制御を維持します。

既存環境では、`supabase/migrations/0028_booking_page_mode.sql` **だけ**をSupabase SQL Editorで追加適用してください。新規DBでは従来どおり全マイグレーションを順番に適用します。設定用テーブル `store_booking_preferences` と保存RPCを追加するだけで、既存予約の移行・削除、Google OAuthのスコープ追加、接続のやり直しはありません。

保存は管理者のみ可能です。APIは認証情報の店舗IDを利用し、クライアント指定の店舗は受け付けません。設定テーブルはanon/authenticatedからの直接操作を許可せず、service_roleにはSELECTと保存RPC実行のみ許可します。未設定店舗の初期方式はメニュー方式です。SQL未適用でも従来のメニュー方式を表示し、管理画面の保存は無効にします。その他のDB障害や不正な設定値では、異なる画面へ切り替えず再読み込みを案内します。

Workersのプラン変更も行いません。メニュー数・担当者数が増えた際の本番CPU時間は別途メトリクスで確認してください。

## 確認

- `tests/date-availability.test.ts`: 既存の担当者別計算との一致、長短メニュー、準備・片付け、日跨ぎ、休業、スタッフ・メニューの公開制限、取得失敗時の受付停止。
- `tests/date-availability-api.test.ts`: 店舗スコープ、日付・受付期間、外部照会中に締切を過ぎた場合、no-storeとエラー時の情報制限。
- `tests/date-first-booking-ui.cjs`: PC/スマートフォンで日時→メニュー・担当者→確認→競合時の選び直し→確定、連絡先の保持、空きの消滅、通信失敗と再確認、日付変更後の古い応答の破棄。APIはすべて模擬し、実際の予約・外部通知は行いません。
- 既存の予約画面・予約保存中の競合・変更・キャンセル・通知に関するチェックも継続します。
- `tests/booking-mode.test.ts`、`tests/booking-page-mode-db.sql`、`tests/booking-page-mode-ui.cjs`: 店舗ごとの保存、権限、未適用・通信失敗時の処理、設定の再読み込み、公開画面の完全な分離、入力中のページを維持する動作を確認します。
